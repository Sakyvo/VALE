# 展示用纹理资产迁出主仓库，托管于 Cloudflare R2

`thumbnails/` 曾是主仓库的一部分并随 `build.yml` 的 `path: '.'` 整体发布到 GitHub Pages。741 个包时它已占 632MB，而 GitHub Pages 的**已发布站点硬上限是 1GB**、`.git` 已达 4.72GB。按每包中位数 682KB 推算，目录扩到约 3900 个包会使站点体积达 2GB 量级，Pages 部署会直接失败，仓库也会撞上 5GB 红线。因此展示用纹理不再进入主仓库，改为托管在 Cloudflare R2 并通过 `assets.vale.cc.cd` 分发；主仓库只保留代码、索引、SBI 分片和生成页面。

选择 R2 而非"独立 `Sakyvo/assets-NNN` 仓库 + jsDelivr"：后者虽能复用 `packs-NNN` 的现成上传逻辑且零成本，但要把约 13 万个小 PNG 塞进一个 git 仓库，clone/push 代价高，且 jsDelivr 逐文件回源的冷启动和大仓库滥用阈值都不可控。站点本就在 Cloudflare 之后，R2 的自定义域和免费出站是同一套基础设施的原生能力。也评估过"仅靠激进瘦身留在仓库内"——瘦身确实能把 632MB 压到 60-80MB 量级，但 `.git` 的历史体积不会因新文件变小而收缩，只有让纹理彻底不进仓库才能止血。

R2 上只放降采样后的展示版（图集类 ≤512、物品/方块类 ≤256，仅 2 的幂次 + nearest，以保证图集精灵切片坐标严格对齐并维持像素风格）。**全分辨率母本在本地 gitignored 目录保留，并且是 SBI 指纹生成的唯一输入**——`generate-sbi-data.js` 用 `kernel: 'nearest'` 直接采样到 16×16/32×32，最近邻的采样点位置取决于缩放比，用瘦身版生成会让全站 pix 整体位移、group 哈希全变。母本丢失不是不可逆的：随时能从 `packs-NNN` 重新提取，代价是重下约 70GB 并重跑提取。
