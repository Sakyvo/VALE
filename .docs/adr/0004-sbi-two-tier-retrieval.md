# SBI 采用两级检索：粗排分片剥离 `pix`，精排按需拉取

`pix`（`diamond_sword` / `ender_pearl` 为 32×32 RGBA，其余 16×16）占 `data/sbi-fp/` 分片体积的 **89.9%**，`dhash`+`sig`+`hist`+`moments`+`edge` 合计仅 10%。655 组时分片总量 18MB、典型搜索需下载约 15MB；扩到约 2700 组会变成约 74MB / 单次搜索约 63MB，移动端不可用。因此分片拆成两级：粗排分片只含轻量特征，全类型约 8MB、按类型分片后典型搜索约 5MB；粗排产出 top-K 组后，只拉取这些组所在的 `pix` 分桶（每桶约 64 组），约 0.5-1MB。总下载约 6MB，而 `pix` 仍然全程参与最终打分，**精度上限不变**。

不采用"压缩 `pix` 本身"：16×16 RGBA 降到 alpha 掩码 + 8×8 RGB 虽能减约 78% 体积，但 2700 组仍要下载约 20MB，且颜色降采样会直接削弱 `compareSpatial` 的 color / colorDirection 项——用精度换体积，且只是把撞墙时间推后。也不采用 VPS 方案（`.docs/SBI_VPS_PLAN.md`）：它能让客户端零下载且精度不必妥协，但会推翻"SBI 必须维持静态托管兼容性"这条核心约束，并引入持续成本和运维。VPS 保留为两级检索实测仍不达标时的升级路径。

两级检索的唯一风险是**召回**：真值若掉出粗排 top-K，精排救不回来。现有的 sig 桶索引选择性有限（`diamond_sword` 仅 46 个桶、最大桶占 12.7%，±1 邻域展开后候选集仍是全库的一大半），dhash 分段索引选择性好得多但要求 4 字节精确匹配、对 JPEG 压缩截图脆弱。因此新增合成自匹配语料（用每个包自身纹理按 `generate-sbi-data.js` 已有的 sprite 布局合成 hotbar+HUD 截图）叠加 JPEG/缩放/亮度退化，用于测量 recall@K。合成语料是**开发期诊断工具，不是验收标准**；验收仍是 `test_img/` 九张真实截图组级 9/9。
