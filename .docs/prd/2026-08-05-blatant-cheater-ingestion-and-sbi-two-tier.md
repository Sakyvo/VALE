# 大批量投稿入库与 SBI 检索架构重构

## Problem Statement

站点目录只呈现了它实际拥有的一部分内容，而即将到来的一批投稿会把这个缺陷放大成彻底不可用。

作为站点维护者，我手上有一位投稿者分两批传来的 2666 个唯一材质包（其中 2201 个尚未入库，共 53.2GB），我希望把它们全部上线、可浏览、可下载、可被以图搜图找到。但当前站点撑不住：

- 主页搜索 "fye" 返回 0 条结果。不是搜索坏了——**378 个包已经上传到远端、已经在 List 里，却因为提取流程在 `packs-004` 中途断掉而从未生成过展示数据**，站点上完全不存在。registry 有 1118 条，公开可见的只有 738 个。三分之一的目录是隐形的。另有 37 个本地包从未上传。
- `thumbnails/` 已占 632MB 并随整个仓库发布到 GitHub Pages，而 Pages 的已发布站点硬上限是 1GB，`.git` 已达 4.72GB。按当前每包体量，目录扩到约 3900 个包会让站点体积达 2GB 量级，**部署会直接失败**。
- SBI 指纹分片 18MB、典型搜索需下载约 15.3MB；扩到约 2700 组会变成约 74MB / 单次搜索约 63MB，**移动端无法使用**。
- 来料里仅名字含 "eum3" 的就有 211 个，而九张回归测试图里五张属于 Eum3 家族、四张的领先优势低于 0.02（最低 0.0046）。这些近乎同款的兄弟包一旦入库，**现有的以图搜图结果会被挤掉**。

我需要的不是"把包传上去"，而是让站点在四倍规模下仍然能部署、能浏览、能准确搜图。

## Solution

分四个阶段推进，每个阶段结束都有可验证的产出，任何一阶段失败都不会污染前一阶段的成果。

**① 展示资产迁出主仓库。** 缩略图不再进入 git 仓库和 Pages 发布物，改为托管在 Cloudflare R2 并经 `assets.vale.cc.cd` 分发。同时按用途分级降采样（图集类 ≤512、物品/方块类 ≤256、封面不动），把展示资产总量压掉约四分之三。全分辨率母本留在本地 gitignored 目录，作为 SBI 指纹生成的唯一输入。

**② 补齐存量缺口。** 补提取那 378 个隐形包、补传那 37 个从未上传的包。搜 "fye" 会有结果，目录规模从 738 涨到约 1150。这同时是新资产管线的第一次真实压力测试。

**③ SBI 改为两级检索。** `pix` 字段占分片体积 89.9%，把它从粗排分片里剥离，改为粗排产出候选后按桶按需拉取。典型搜索下载量从约 63MB 降到约 6MB，而 `pix` 仍然全程参与最终打分，精度上限不变。同时把 group 等价从"全部纹理指纹完全相同"放宽为"在本次查询实际用到的证据面上像素级不可分"——真正看不出区别的兄弟包并列展示，而不是赌其中一个。

**④ 投稿包分批入库。** 先 50 个包试跑完整链路，确认无误后按目标仓库分批（每批约填满一个 `packs-NNN`），每批走完整的四阶段审批。所有包上传前一律先过规范化。

用户视角的最终状态：主页能浏览到全部约 3900 个包（含投稿包，带来源区分），`/l/Blatant Cheater/` 是这批投稿的独立入口，以图搜图在四倍语料下仍然秒回且九张回归图全部命中。

## User Stories

### 目录完整性

1. 作为站点访客，我想在主页搜索 "fye" 能搜到 Fyes 系列材质包，这样我就不会以为站点没有收录它们。
2. 作为站点访客，我想浏览到 registry 里所有已上传的包，这样目录数量与实际藏量一致，不会有隐形条目。
3. 作为站点维护者，我想知道每个已上传的包是否真的生成了展示数据，这样提取中断不会再悄无声息地吞掉三分之一目录。
4. 作为站点维护者，我想让补提取能力复用已有的远端下载路径，这样不必给提取脚本新增一条平行的远端能力。
5. 作为站点维护者，我想让本地已有 zip 的包直接从本地补提取，这样 378 个里的 373 个不需要重新下载。
6. 作为站点维护者，我想让本地缺失的少数包（5 个）自动从对应的 `packs-NNN` 拉取后补提取，这样不必人工找文件。
7. 作为站点维护者，我想让 37 个从未上传的本地包按正常入库流程补传，这样它们和其他包遵循同一套规范化与识别规则。

20. 作为站点维护者，我想让仓库容量到达上限时自动滚动到下一个编号，这样不必手工计算每个包该放哪。

## Implementation Decisions

### 展示资产托管

- 展示用纹理迁出主仓库，托管于 Cloudflare R2，经自定义域 `assets.vale.cc.cd` 分发。理由与被拒方案见 `.docs/adr/0003-thumbnail-assets-off-repo.md`。
- 新建一个资产远端抽象模块，形状照抄现有的 `github-pack-remote`：导出工厂函数、URL 构造函数、路径/对象名校验函数。上传逻辑不直接内联进业务脚本。
- 材质包名普遍含 Minecraft 色号（`§`）、`#`、空格，URL 编码在既有代码里已经是出错点，资产 URL 构造必须集中在这一个模块里并被单独测试。
- 前端引用缩略图的位置改为从一个资产基址常量拼接，而不是硬编码 `/thumbnails/`。基址在构建期注入，本地开发可回落到本地目录。
- 上传具备幂等性：同一对象重复上传不产生副本；中断后重跑跳过已验证对象。

### 展示版降采样

- 降采样规则实现为纯函数：输入文件名与原始尺寸，输出目标尺寸或"保持原样"。所有分级决策集中于此，不散落在图片处理流程里。
- 分级上限：图集类（粒子、物品栏、GUI 图标、原始物品栏）≤512；物品与方块类 ≤256；封面保持原样；包图标压到 256。
- 只允许 2 的幂次缩放，且必须使用最近邻采样。前端的护甲、GUI、物品栏预览按固定坐标切图集精灵，非 2 幂次会让切片错位；非最近邻会毁掉像素风格。
- 原始尺寸已低于目标上限的文件不做处理。

### 全分辨率母本

- 母本存放于本地 gitignored 目录，是 SBI 指纹生成的唯一输入。
- 指纹生成端用最近邻直接采样到 16×16（钻石剑与末影珍珠为 32×32），采样点位置随缩放比变化，用降采样版生成会让全站像素特征整体位移、组标识全部失效。
- 母本可从 `packs-NNN` 重建（代价约 70GB 重下 + 重跑提取），因此不属于不可恢复数据。

### 存量缺口补齐

- 补提取复用现有替换流程里的远端下载路径，不给提取脚本新增平行的远端能力。
- 优先使用本地已有归档（378 个里 373 个本地存在），仅对本地缺失的少数包走远端下载。
- 补传的 37 个包走完整入库流程，与投稿包遵循同一套规范化、识别与重复判定规则。
- 补提取完成后重新生成索引、页面与指纹，此时语料从 655 组增至约 1000 组，是第一个真实规模压力点。

### SBI 两级检索

- 分片拆为两级：粗排分片只含轻量特征（感知哈希、签名、直方图、矩、边缘强度）；像素数据独立成桶。设计依据与被拒方案见 `.docs/adr/0004-sbi-two-tier-retrieval.md`。
- 粗排产出候选组后，只拉取这些组所在的像素分桶。桶的粒度约为数十组，使命中桶数远小于总桶数。
- 分片元数据描述每个逻辑分片包含哪些桶文件，客户端据此按需拉取；单个桶文件体积仍受既有的分片体积目标约束，超出时按确定性键继续拆分。
- 像素数据仍全程参与最终打分，精度上限不变。
- 粗排召回是本方案唯一的新增风险，必须被测量而非假设。

### 组等价

- 组标识从"全部可观测纹理的完整指纹拼接哈希"放宽为"在本次查询实际用到的证据面上像素级不可分"。理由见 `.docs/adr/0005-observable-group-equivalence.md`。
- 稀有度权重按新的组定义重新计算，避免同一批不可区分的包被重复计数而虚高权重。
- 端到端验收判定保持组级不变：期望包必须存在于某个被完整打分的组，且该组排第一。
- 指纹版本常量与客户端缓存标识同步推进。

### 合成评估语料

- 用每个包自身的纹理，按指纹生成端已有的精灵布局坐标，合成快捷栏与状态栏截图。
- 叠加退化增强：JPEG 重编码、缩放、亮度与对比度扰动。
- 作为端到端测试工具的新模式接入，不另建一套 harness。
- 产出三类指标：粗排召回率、组级排名第一率、互相不可区分的包集合。
- 明确定位为开发期诊断工具，不是验收标准，不用于对外描述精度。

### 投稿入库

- `less` 与 `more` 仅为投稿者的两次传输批次，合并为单个 `Blatant Cheater` List。两者仅 88 个同名文件（79 个字节相同），不是包含关系。
- 投稿包不加入 `Sakyvo` List。`Sakyvo` 的语义是站点自有收藏，定义见 `CONTEXT.md`。
- 投稿包出现在主页网格。主页归属与是否自有无关。
- 归档继续存放于 GitHub `packs-NNN` 仓库，沿用满仓标记与自动滚动机制。当前 `packs-006` 尚有余量，其后约需新建 11 个仓库。
- 所有包上传前一律先过规范化，只有规范化产物可以上传。
- 超过 100MB 硬限的包先经规范化的冗余清理再判定尺寸；仍超限的记为待处理并保留审计原因，不为其新开存储通道。
- 高版本材质与 Overlay 的识别沿用现有实现，不因这批投稿调整规则。
- 视觉内容重复的包在仓库分配与远端写入之前被拦下，沿用现有的哈希绑定决策流程。

### 执行节奏

- 先用 50 个包跑通完整链路：规范化 → 上传 → 提取 → 降采样 → 资产上传 → 索引与页面生成 → 指纹重生成 → 回归。
- 确认无误后按目标仓库分批，每批走完整四阶段审批，每阶段需要与审阅结果绑定的摘要。
- 每批完成后跑轻量回归；全部完成后跑完整重生成、完整回归、合成语料全量评估与规模化性能测试。

### 主页加载路径

- 修复卡片可见回调里的线性查找，改为构建期或初始化期预计算的名称到序号映射。

## Testing Decisions

好的测试只断言外部可观测的行为：给定输入产生什么输出、给定状态发生什么转移、契约是否被遵守。不断言函数被调用了几次、不断言内部变量名、不断言实现里出现或不出现某个 API。性能不写单元测试——性能靠可复现的规模化测量与人工验收。

复用 4 个既有接缝，新增 2 个。

`tests/generate-sbi-data.test.js` 已经直接引入生成端的导出函数并在临时目录里验证分片产物。这里覆盖：

- 两级分片的切分结果：粗排分片不含像素数据，像素桶包含且仅包含预期组。
- 像素分桶的分配是确定性的：同样输入产生同样的桶归属。
- 组等价放宽后的分组结果：在证据面上不可分的包合并、确实有差异的包不合并。

- 分片元数据正确描述逻辑分片到桶文件的映射。

## Further Notes

**待核实事项**：Cloudflare R2 免费额度的确切数字在本次讨论中未能联网确认。按分级降采样后的估算，全量约 3900 个包的展示资产约 790MB，预期在免费额度内，但**开始阶段 ① 之前必须确认一次**。若额度不足，分级上限可以进一步收紧到统一 256（估算约 320MB），这不影响其他任何决策。

**风险集中点**：整个方案里唯一没有先例可循的是粗排召回率。若真值掉出候选集，精排无法挽回。这是新增合成评估语料的直接动机，也是为什么阶段 ③ 必须在阶段 ④ 之前完成——否则 2201 个包会先生成一套注定要重做的分片。

**规模基线**：当前 registry 1118 条、公开 738 个、SBI 覆盖 694 包 / 655 组。阶段 ② 后约 1150 个包 / 约 1000 组。全部完成后约 3900 个包 / 约 2700 组。

**margin 现状**：九张回归图中四张的领先优势低于 0.02（最低 0.0046）。来料含 211 个名字带 "eum3" 的包，而九张里五张属于该家族。这不是"可能会退化"，而是"按现有组定义几乎必然退化"——组等价放宽不是优化，是必要条件。
